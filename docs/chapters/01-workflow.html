第一章 导论：AI × 计量工具的生态谱系与范式分野

1.1 四条技术路线：从”生成代码”到”组织级调度”

AI 进入计量实证，不是一条路，是四条完全不同的路。

第一步必须先给学员装上”路线识别”的眼镜，否则后面的所有对比都会变成参数比较。

路线 代表形态 AI 与 Stata 的关系 人的角色 典型卡点
L1 文本生成 通用对话模型 AI 只写代码文本，人复制粘贴回 Stata 运行 代码搬运工 幻觉参数、版本不匹配、“在我这能跑”
L2 会话内执行 IDE 内嵌插件（TraeWork 类） AI 在 IDE 会话里同步调用 Stata，跑完看结果再下一步 调试者 串行阻塞，一条命令一批结果，批量任务极慢
L3 运行时可编程 DeepSeek Harness 类 AI 在沙箱 Runtime 里编排工具链，自定义循环 Agent 工程师 门槛高，与办公协作体系弱耦合
L4 组织级调度 豆包工作 + AIStata MCP /Stata-Kernel-Jupyter等 AI 把任务委派给后台子智能体并行执行，主会话保持可交互 研究设计者 + 调度者 批次有锁，需按批调度

总结：：

L1 让 AI 帮你写；L2 让 AI 陪你跑；L3 让 AI 自己会跑；L4 让一组 AI 替你跑，而你还在跟人讨论下一步怎么做。

L4 的差别不在”模型更强”，而在时间结构变了：算力等待从”人盯着屏幕”变成”后台并行推进”，认知带宽从”一次一个任务”变成”边跑边设计”。

1.2 组织智能体范式：委派—并行—校验—交付

一次完整的组织智能体任务，包含四个阶段，缺一不可：

[设计] 主会话：确定识别策略、列出独立子任务清单
   ↓ 委派（一次性下发整批）
[执行] 后台子智能体池：每个子任务独立跑 Stata，互不阻塞
   ↓ 各自产出 do / log / 图 / 结果行
[校验] 汇总智能体：检查 log 完整性、符号一致性、显著性、样本量
   ↓ 冲突与失败项单独标记
[交付] 主会话：收到交付包，继续批注、修订、发起下一批

四个阶段对应四个必须讲清的概念：

  1. 委派（Delegation）：不是”让 AI 继续干”，而是”把一段可独立完成的工作切出去”。切分的质量决定并行度。

  2. 并行（Parallelism）：并行的前提是子任务之间无数据依赖。同一份清洗数据上的不同安慰剂检验可以并行；“清洗 → 回归”不能并行。

  3. 校验（Verification）：交付前必须有机器可判定的校验，不能只靠”看起来对”。最小校验集：log 无 r(####) 错误码、系数符号与预期一致、样本量与基准一致、p 值与置信区间自洽。

  4. 交付（Delivery）：交付物是包而非一段话——do、log、图、结果行、汇总矩阵，五件齐全才算交付。

为什么”主会话不阻塞”在科研里是刚需

实证研究的真实节奏不是线性写代码，而是”跑着等、等着想、想着改”。传统 Agent 工具在这三步里只能做第一步；一旦 Agent 开始跑，研究者的思考被迫中断。L4 的价值在于：你可以一边等 200 次置换检验跑完，一边跟合作者讨论”要不要加一个 2015 年政策叠加的排除”，讨论完回来，结果已经在飞书表里。

同时必须讲清的能力边界（不回避）

  • 一批委派未交付，不能开第二批。这是调度锁，不是性能问题。

  • 因此真实的科研节奏是”批次化”而非”流水线化”：设计好一批 → 跑 → 评审 → 下一批。

  • 这个约束反而逼近真实科研的评审节奏：每一批检验都对应一次”导师看过、提过意见”的环节，天然留下评审痕迹。

1.3 在 AIAgent 里面跑 Stata的MCP 是什么、不是什么

是：一个把 Stata 进程封装成标准化工具接口（MCP 协议）的服务端。模型通过结构化调用执行 do 代码、读取 log、取回返回值、接收生成图片、查询帮助、安装外部命令。

不是：

  • 不是把数据上传给大模型的通道。数据留在你的本地或服务器 Stata 实例里，出去的是指令和回执。

  • 不是”AI 自动理解计量经济学”。它执行你让它执行的，不会替你判断识别假设是否成立。

  • 不是版本管理器。可复现性仍要靠 do 文件规范、种子、包版本记录。

典型后端两种：

后端 机制 优点 代价
pystata 常驻会话 Stata 官方 Python 接口，进程常驻，状态可延续 快、可跨调用保留内存数据、便于交互式探索 需匹配 Stata 版本与 Python 版本；内存占用
batch 批处理 每次调用 stata -b do file.do，读 log 隔离干净、可复现性最好、崩溃不影响其他任务 每次启动开销；状态不延续

推荐：探索阶段用 pystata，交付与复现阶段强制切 batch 模式。

1.4 横向对比：豆包工作+AIStata vs DeepSeek Harness / Workbuddy / TraeWork

大家最关心的”我为什么要换工具”。

对比只讲定位差异，不做优劣评判。

维度 豆包工作 + SKJMCP DeepSeek Harness Workbuddy TraeWork / AI IDE
一句话定位 组织协同 + 异步并行的实证科研调度台 可编程 Agent 运行时沙箱 通用 AI 工作台（办公+轻代码） AI 原生代码 IDE
任务调度 委派后台并行，主会话非阻塞 单沙箱内脚本编排循环 串行为主，轻量子任务 会话内单 Agent 串行
等待体验 派出去就能继续讨论 需自行写异步/多进程 基本要等 必须等当前任务结束
Stata 执行 AIStata MCP 接真实 Stata，保留 License 与数据主权 需自行接 MCP 或 API 以生成代码为主，执行需接入MCP 内置 MCP，也是需要接入配置
协作底座 原生飞书：文档/多维表/云盘/权限/评论 弱耦合，需自建 API 对接 可对接飞书但无组织级委派范式 本地文件系统 + Git
最适场景 课题组批量稳健性、多项目并行、导师评审核验 Agent 框架二次开发、自定义流水线 日常办公 + 实证分析 单人沉浸式写 do、调 bug
明显短板 批次锁；MCP 需自部署 门槛高，不适合社科研究者 缺面向因果批量检验的调度原语 团队协作与评审闭环弱
学术产出链路 结果 → 多维表 → 文档 → 版本留痕 产出留沙箱，需手动同步 手动导出上传 留本地，靠 Git 版本

差异化总结（口播版，四句）

  • DeepSeek Harness：给会写 Agent 的人造引擎；

  • Workbuddy：给所有人一个聪明的办公助手；

  • TraeWork：给一个人一个会写 Stata 的 IDE；

  • 豆包工作 + AIStata MCP：给一个课题组一套能批量跑检验、能在飞书里逐条核验的科研生产系统。

避免踩坑

  1. 对比不是说”谁更强”。学员里已经在用 TraeWork、VsCode等，要给他”何时切换”的判断标准。

  2. 不要夸大并行收益。并行只对无依赖任务有收益；识别策略设计、数据清洗、基准设定这些核心环节，并行帮不上忙。

第二章 环境搭建：三件套部署与连通性验证

2.1 环境清单与版本矩阵

组件 最低 推荐 说明
Stata 16/17 18 / 19 17 起 pystata 稳定；18+ 对 didregress、causal 支持更好
Python（若用 pystata 后端） 3.9 3.11 / 3.12 必须与 Stata 官方支持的 Python 版本匹配
Node（若用 Node 版 MCP server） 18 20 / 22 版本过低会导致 MCP 传输层报错
操作系统 Win10 / macOS 12 Win11 / macOS 14（Apple Silicon 需确认 Stata 为 ARM 原生版） Rosetta 下 pystata 常有路径问题
网络 可访问 SSC / 包镜像 内网镜像 外部命令预装是部署成败关键

2.2 AIStata MCP 的两种部署形态

形态 A：IDE 内嵌服务（单机自用）

  • 场景：个人笔记本、单篇论文、快速探索

  • 特点：随 IDE 启动，配置集中在一个 json；适合单任务范式

  • 缺点：与本机强绑定，多人无法共享；IDE 关闭即服务消失

形态 B：MCP Server

2.3 服务端配置与外部命令预装

配置要点（四项）

  1. Stata 可执行路径：Windows 指向 Stata18.exe（或 StataMP-64.exe），macOS 指向 Stata.app/Contents/MacOS/Stata。

  2. 工作目录白名单：只允许访问项目目录，禁止全盘。这是安全底线，不是可选。

  3. 超时与内存：单任务超时（建议 600–1800 秒，置换类任务放宽）、set maxvar（宽面板必需）。

  4. 图片与日志落盘：明确 figure 输出目录、log 目录，并让 MCP 返回可访问路径。

外部命令预装清单（按课程模块分组）

分组 命令 用途
基础 reghdfe ftools estout outreg2 coefplot 高维固定效应、表格、图形
DID csdid drdid did_imputation eventdd did_multiplegt_dyn alldid 交错 DID、事件研究、异质性稳健
匹配 psmatch2 teffects（内置） cem（可选） PSM、平衡性检验
RDD rdrobust rddensity rdlocrand 断点回归与密度检验
合成控制 synth synth_runner sdid SCM、合成 DID
门槛/非线性 xthreg 面板门槛
空间 xsmle spmat spregress（内置 sp 系列） 空间面板、空间权重
机器学习 ddml pystacked lassopack 双重机器学习、堆叠、LASSO
动态 pvar lpirfs xtset 配套 PVAR、局部投影

预装三条铁律

  1. 装完立即 which <cmd> 逐条验证，输出写入 env_manifest.log；

  2. 记录每个包的版本（ado describe <cmd> 或看 ado 文件头），写进项目 ENV.md；

  3. 不要在交付后才装包。装包动作必须发生在批次执行之前，否则并行子任务会各自触发安装、相互抢占、甚至互相覆盖。

2.4 在豆包工作中接入为技能

接入四步（结构）

  1. 新建项目空间（一门课/一个课题一个空间，避免串味）

  2. 添加自定义技能，填入 MCP 服务地址与传输方式（stdio / HTTP）

  3. 开启工具权限：代码执行、文件读写、图片返回、帮助查询

  4. 绑定飞书连接器：多维表格写入、文档创建、云盘上传

接入后必须验证的三类信号

  • 工具可见：会话里能触发 Stata 执行工具，而不是”我以为它会调”

  • 回执完整：一次调用回来的是 log + 返回值 + 产物路径三样，缺一即为配置不全

  • 失败可读：故意跑一条错命令（如 reg yyy xxx），确认返回的是可读错误码与 log 片段，而不是”执行失败”

教学坑点提醒：很多学员卡在”看起来接上了，实际没回执”。判断标准很简单——能不能拿到 log 文本。拿不到 log 的接入，等于没接入，后面所有可复现性都无从谈起。

2.7 常见故障树

现象 最可能原因 处置
调用无响应 服务未启动 / 端口被占 查进程、换端口
返回空 log 后端 batch 模式未正确重定向日志 显式 log using 并回读
r(601) 文件不存在 工作目录非预期 强制绝对路径 + 目录白名单
图片不返回 export 路径不在白名单 / 格式不支持 统一导出 png 到固定目录
中文乱码 编码或字体 do 文件 UTF-8；图中文字用英文或指定字体
并发任务互相覆盖 共享 workdir 每子任务独立目录（关键）
包找不到 未预装 / 个人 ado 路径 预装 + which 验证 + 统一 ado 路径
超时 置换/自助类任务过长 提高超时 / 拆小批次 / 减少重复次数
